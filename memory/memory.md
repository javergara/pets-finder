# memory.md — memoria de procesos del agente (append-only)

Registro de decisiones de proceso, comandos clave, aprendizajes y gotchas. No es un changelog de producto (eso es `changes.md`/`CHANGELOG.md`); es memoria de **cómo trabajar en este repo**.

## 2026-07-31 — Bootstrap del proyecto

- **Hallazgo clave:** el directorio de trabajo no estaba vacío al empezar — ya contenía diseño real para "Adopta" (no "PawMatch") generado con DesignSync en una sesión previa (`design/prototypes/HANDOFF.md` + 3 prototipos `.dc.html`). Antes de asumir un scaffold genérico, **siempre revisar primero si ya existe trabajo previo relevante en el directorio** (`ls -la`, leer cualquier `HANDOFF.md`/README antes de sobrescribir). Se decidió con el usuario usar ese diseño como fuente de verdad de producto en vez de descartarlo — evitó rehacer un análisis y diseño ya hechos.
- **Gotcha de git:** no había identidad de git configurada (ni global ni local) en la máquina. `git commit` falla sin `user.name`/`user.email`. Se resolvió configurando identidad **solo local a este repo** (no se tocó `~/.gitconfig`), con autorización explícita del usuario — nunca asumir y correr `git config --global` sin preguntar.
- **Decisión de stack confirmada con el usuario:** FastAPI+SQLAlchemy+SQLite local en vez de Supabase/Firebase (que sugería el HANDOFF.md original), porque el alcance del MVP no incluye chat en tiempo real. Ver ADR 0001. Si en el futuro se aborda la feature `11-chat` (backlog), reevaluar esta decisión con un ADR nuevo, no asumir que hay que migrar automáticamente.
- **`init.sh` diseñado para ser tolerante en fases tempranas:** antes de que exista código de producto (`src/api`, `src/web`), los pasos de lint/test/instalación deben **omitirse con aviso claro**, no fallar — solo deben fallar los pasos que sí tienen algo que verificar (validación de `feature_list.json`, dependencias del sistema). Si `init.sh` empieza a fallar "porque no hay nada que testear todavía", es una señal de que el script está mal diseñado, no de que el proyecto esté roto.
- **`feature_list.json`:** la regla de "máximo un `in_progress`" se verifica en tres capas independientes por diseño (no es redundancia accidental): el hook local de `.pre-commit-config.yaml`, `scripts/validate_feature_list.py` (usado por `init.sh`), y (Fase 5) el hook de `.claude/settings.json`. Si se cambia esta regla, hay que actualizar las tres.

## 2026-07-31 — Fase 5: harness engineering

- **Gotcha de pre-commit:** el `rev: v3.3.3` puesto a ojo para `pre-commit/mirrors-prettier` no existe en el repo real (la última tag estable es `v3.1.0`; hay tags `v4.0.0-alpha.*` pero no una `v3.3.x`). `pre-commit install --install-hooks` falla recién al clonar el repo del hook, no al escribir el YAML — **siempre correr `pre-commit install --install-hooks` de verdad al menos una vez** para descubrir tags inválidos, no basta con que el YAML sea sintácticamente válido. Si hace falta verificar una versión sin acceso al navegador, `git ls-remote --tags <url>` funciona.
- **Diseño de `init.sh`:** confirmado en la práctica — corrió en verde con `src/api`/`src/web`/`scripts/seed.py` inexistentes, omitiendo cada paso no aplicable con aviso, y solo fallando en la validación real de `feature_list.json` y en la instalación real de git hooks. Este es el patrón a mantener cuando se le añadan pasos nuevos en Fase 7 (no hacer que "no hay nada que testear" sea un error).

## 2026-07-31 — Fase 7: implementación del MVP

- **Gotcha de `init.sh`:** detectar si `src/web/package.json` tiene un script `lint`/`test` parseando `npm run --silent` con grep es frágil — `--silent` directamente **suprime** el listado de scripts (queda vacío), así que el grep nunca matchea y el paso se marca como "omitido" aunque el script sí exista. Se reemplazó por `node -e "process.exit(require('./package.json').scripts.lint ? 0 : 1)"`, que lee el JSON directamente. Lección: para detectar config/scripts de una herramienta, leer el archivo de config directamente en vez de parsear el output human-friendly de un comando.
- **Decisión de stack frontend (ejecución):** el scaffold de Vite (`npm create vite@latest -- --template react-ts`) trae `oxlint` en vez de `eslint` como default de sus plantillas actuales. Se mantuvo `oxlint` (más rápido, cero config) en vez de forzar `eslint` como decía `docs/conventions.md` originalmente — se corrigió el doc para reflejar la herramienta real, no al revés (ver `CHECKPOINTS.md`: la documentación no debe describir un comportamiento que el código no tiene).
- **Tailwind v4:** se usó `@tailwindcss/vite` + directiva `@theme` en `index.css` (no `tailwind.config.js`/PostCSS) — es el flujo nuevo de Tailwind v4, más simple que la Fase 3 anticipaba genéricamente.
- **`datetime.UTC`:** el intérprete real disponible es Python 3.10.17, no 3.11 — `datetime.UTC` (alias que ruff/UP017 sugiere) solo existe desde 3.11 y hubiera roto en tiempo de ejecución. Se corrigió `pyproject.toml` (`target-version = "py310"`) para que ruff deje de sugerir una API que no existe en el intérprete real, en vez de aplicar el fix sugerido a ciegas.
- **Verificado con navegador real** (Chrome vía herramientas de automatización): deck de swipe con fotos reales, click en ♥ crea el match y muestra el modal, "Ver mis matches" lista el match con su score de afinidad, la ficha de mascota muestra la explicación de afinidad y las acciones de salud/refugio. Sin errores en consola. DB reseteada al estado limpio del seed después de la prueba manual.
